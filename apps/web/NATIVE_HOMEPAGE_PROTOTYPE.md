# Native homepage prerender prototype

This prototype adds `/` to the existing React Router prerender list only when `PRERENDER_HOMEPAGE=true`. The default build remains SSR. React Router writes the matching route HTML and loader data; browser cart state is still loaded separately.

## Staging setup and checks

1. Connect the existing `glfonline-web-staging` Worker to the prototype branch in Cloudflare Workers Builds and confirm the build deploys to that Worker. The repo's Wrangler config defaults to the production name `glfonline-web`; if the deployment command invokes Wrangler directly, it must include `--name glfonline-web-staging --keep-vars`. Set `PRERENDER_HOMEPAGE=true` and `SANITY_DATASET=staging` in build variables, and keep `SANITY_DATASET=staging` on the Worker at runtime. Make the Shopify Storefront API URL and access token available to the server-side build as protected build variables/secrets and to the Worker at runtime as appropriate; Worker secrets are not automatically available to build steps. Do not expose the token in client build variables or client code.
2. Add a Sanity staging webhook for publish, unpublish, and update events that affect the homepage or main navigation. Point it directly at the staging Worker's native Cloudflare Deploy Hook. Treat the hook URL as a secret; anyone with it can start builds.
3. Publish a harmless staging homepage edit. Record the Sanity publish time, webhook delivery, Workers Build start and finish, and when the new text appears in both `/` HTML and the matching `/_.data` response (including its `_routes` query). Repeat after editing main navigation. The staging dataset uses Sanity's uncached API so the build reads the latest published content; production keeps the existing API CDN endpoint.
4. Trigger a code build and a content build close together. Observe which versions deploy and whether the later build includes the latest code and content. Cloudflare documents deduplication only while an identical hook's build is queued or initializing; it creates another build after that point. Build ordering and the resulting artifact freshness still need this live test.
5. Cause a controlled staging build failure, such as temporarily making the staging homepage document invalid, then restore it and rebuild. Confirm what remains served after failure and verify the last known good deployment is still available for rollback. Do not infer this behavior from local builds.
6. Test recovery by recording the current staging deployment, then deliberately miss one webhook delivery. Manually trigger the same native Deploy Hook after publishing another edit and verify HTML plus `/_.data` refresh. A missed webhook has no automatic freshness guarantee.
7. Change Shopify shop metadata in a staging-safe way and confirm that its root-loader value changes only after a code/content build. Shopify metadata has no Sanity trigger; arrange a separate trigger or manual rebuild if it needs refresh.
8. Locally, put only `SANITY_DATASET=staging` in ignored `apps/web/.dev.vars` so the emulated Worker prerender uses staging too. On staging, verify `/` GET and HEAD, `?utm_source`, `?cart=open`, a session cookie, and `/_.data` (including its `_routes` query) serve the expected asset or Worker response; use tail or invocation data to record actual routing and any Worker render as a gap against the static-homepage goal. Check the cart count, drawer close, and back navigation with a populated test cart, an already-open tab across a code deploy, and that HTML, loader data, and scripts stay on the same build.

Cloudflare's [Deploy Hooks documentation](https://developers.cloudflare.com/workers/ci-cd/builds/deploy-hooks/) describes hooks as HTTP POST triggers and documents duplicate suppression for builds still queued or initializing. It does not establish ordering across overlapping code and content builds or confirm the failed-build and last-good-deployment behavior above; those are staging acceptance checks.

This simple prototype can keep the last good static content indefinitely after a missed webhook, failed build, or upstream failure. It does not enforce the earlier 65-minute outage cutoff or guarantee seven-minute freshness after missed deliveries; production needs an explicit policy decision on those limits.

Existing production rollback remains the recovery path after a deployment. No production build variables, deploy hooks, or deployment settings are part of this prototype.
